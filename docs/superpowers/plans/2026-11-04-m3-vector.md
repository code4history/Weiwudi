## m3-t2: registry の一般化 — 子 Source・資源の型・範囲の持ち主（P1）

コミット種別: `refactor:`（内部。t7 まで外から使われない）

### 対象ファイル

`src/store.ts`（型）・`src/spec.ts`（型と `normalizeMember`）・`src/registry.ts`・`src/core.ts`（`evictScopesFor`）・`src/hook.ts`（`templatesOf` の子の扱いだけ）・`tests/unit/registry.test.ts`・`tests/unit/spec.test.ts`・`tests/unit/core.test.ts`（追記のみ）・`tests/unit/registry-members.test.ts`（新規）

### 作るもの

**子 Source（R1）**: スタイル 1 つは複数の Resource（スタイル・TileJSON・タイル・グリフ・スプライト・データ）を持つ。§5.6 の合流の規則（keep・範囲だけ・leave・`credentialParams` を縮めない）は「1 つの Source が 1 つの資源の指定を持つ」前提で書かれ、m2 の registry もそうなっている。そこで**スタイルの下位資源ごとに内部の子 Source を作り**、registry の規則をそのまま子ごとに当てる。

- `SourceKind` に `'child'` を足す。`SourceRecord` に `parentId?: string`
- 子の id は `${parentId}\0${type}:${論理名}`（X1）。論理名は、スタイルの中で子を指す名前を `encodeURIComponent` したもの: タイル・TileJSON は `sources` のキー（TileJSON の下のタイルは `<キー>/tiles`）、グリフは `glyphs`、スプライトは `sprite`（配列なら `sprite/<id>`）、データは `sources/<キー>/data`、スタイル自身は `style`。`raster`・`vector`・`asset` の Source は子を持たない。利用者の id は `\0` を含めない（m2 R36）ので衝突しない。**同じ URL で範囲の違う 2 つのソースは別の子になり**（URL から id を作ると 1 つにまとまり、片方の範囲が落ちる）、どちらも同じ Resource に合流して範囲が和になる。同じ論理ソースの URL や範囲が変わっても子の id は変わらない（update で Entry を消し直さない）
- 子の記録の `spec`（`StoredSpec`）は `kind: 'child'`・`type`・`logicalName` を持つ
- 子の `order` は親の `order`（資格情報の選び方と照合表の順が親の登録順になる）
- `sources()`・`source()`・`getOwn` は子を見せない（t7 で control を直すまで、子は作られない）。子の判定は `store.ts` の補助 `isChildRecord(rec)`（`rec.kind === 'child' || rec.parentId !== undefined`）1 つで行う
- **同じ id で `kind` を替えた登録は `attribute-invalid`**（C-O5。たとえば `raster` の id で `style` を登録する。子の構成が丸ごと変わり、keep の規則が当たらないため。替えたいときは `remove()` してから登録する）
- **親の `StoredSpec`（スタイル）**: 型・保存・読み出しを t2 で決める（t7 が使う）

```ts
export interface StyleSpec {
  kind: 'style'; id: string;
  url: string;                    // 地図ライブラリへ渡す https の URL（提供元の解決後・資格情報なし）
  templates: [string];            // スタイル自身のテンプレート（正規化済み）
  fonts?: string[];               // m3 では保存だけ。m4 の範囲取得のグリフで使う
  policy: ResourcePolicy; cacheMaxBytes?: number; provider?: string;
  children: { id: string; logicalName: string; type: ResourceType; from?: string }[];  // from は TileJSON の子の id
}
```

  `SourceRecord.spec` は `StoredSpec | StyleSpec | {}`。読み出しは `storedSpecOf`・`styleSpecOf` の 2 つの補助だけで行い、`children` が無い記録は空の配列として読む

**資源の指定を一般化する**（`spec.ts`）

```ts

export function collectTileJson(text: string, base: string): { urls: string[]; scheme?; bounds?; minzoom?; maxzoom? } | undefined;
export interface StripRule {
  credentialParams: readonly string[];
```

**`core.serve` の足し口**（R28・R4）

2. **段階の登録（R2・R3・R30）**: 段 A〜C の途中の状態（control の直列の待ち行列の中で、照合表は最後に作り直す）、`invalid-style` の巻き戻し、オフラインの `update()` で Entry を失わないこと
3. **資格情報の配り先（R5・R21・t3）**: スタイルのオリジンと提供元の `matches` だけに絞る規則に抜けが無いか。TileJSON の `tiles` が別ホスト（Mapbox の `a.tiles.mapbox.com`）でも、提供元の `matches` で付くこと
4. **グリフ（t4）**: 部分ごとの鮮度と削除期限、`EntryMeta.fetchedAt` を最新の部分にした決定（R7）、同時要求のキー
5. 仕様 §5.5・§10・§11・§12 を通して、t5〜t8 の試験の表と突き合わせる
6. 申し送りの表の 12 件が、それぞれの拾い先のタスクの「作るもの」と「試験」に実際に入っているか
7. 第 1 回の指摘の反映（R1・R3・R5・R18・R23・R28・R30 の置き換えと R32〜R37）。範囲は反映した箇所と、そこから波及する t6・t7 の段取りと試験に限る（m2 の第 3 回以降と同じ絞り方）

## Ruling

- R1（事前点検 第 1 回 X1 で id の作り方を置き換えた）: スタイルの下位資源ごとに内部の子 Source（`kind: 'child'`・`parentId`・id は `${parentId}\0${type}:${論理名}`。論理名はスタイルの中の名前を encode したもの）を作り、§5.6 の規則を子ごとに当てる — m2 の registry と §5.6 は「1 Source に 1 資源の指定」で書かれており、規則を書き直さずに済む。子の id は `\0` を含むので利用者の id と衝突しない — 誤りなら registry に Source ごとの複数の指定を持たせる形へ直す（t2・t7 が大きくなる）
- R2: スタイルの登録は段 A（スタイル）→ 段 B（TileJSON）→ 段 C（残り）の順に `applyRegister` を重ね、前の子は最後の段の後にだけ外す — スタイルを `serve()` 経由で取るには Resource が先に要る（§5.5-1）。途中で前の子を外すと update の途中で Entry が消える — 誤りなら段の途中の状態が直列の待ち行列の外から見える（今は照合表を最後に作り直すので捕捉には出ない）
- R3（第 1 回 C-S5 で「取れない」を定めた）: 取れなかった TileJSON から前回作った子は前回のまま残す。「取れない」は Entry が無く上流も失敗したとき（`offline-miss`・`upstream-error`）だけで、`stale` の古い本体は取れたものとして使う — オフラインの `update()` で TileJSON が取れないとタイルの子が外れ、Entry が消える（オフライン用途の中心の場面）。`stale` を失敗にすると、キャッシュがあるのに `fetch-failed` が出る — 誤りなら消えた参照の子が 1 回の update で外れず、次の成功した update で外れる
- R4: `update()` の取得は `revalidate`（hit を飛ばして上流へ。失敗なら古い本体）、`register()` は通常の順 — §5.5 の「オフラインで同じ登録を繰り返しても失敗しない」と §5.5-6 の「update() で取り直し」を両立する — 誤りなら update でも TTL 内は取り直さない
- R5（第 1 回 X2 で置き換えた）: 親の資格情報は、子の**全テンプレート（ミラーを含む）**がスタイルの URL と同じオリジンか提供元の `matches` に当たるときだけ、その子に配る。判定は `style_body.credentialTargetOf` 1 つで、本体の資格情報の除去（R32）も同じ関数を使う — 第三者のスタイルが別のホストを指すと、そのホストへトークンが送られる。ミラーが混ざった子に配ると、照合表の資格情報の選び方（m2 の I2）がオリジンで選ぶので第三者のミラーへ付く — 誤りなら別ホストの認証付きタイルは利用者が別の Source で資格情報を登録する
- R6: スプライトは内部の字句 `{spriteSuffix}`（`(@2x)?.json|png`）で 1 つの Resource にし、利用者の登録では受けない — §5.3 の「残りのパス」を照合で取る形が要る。§4.2 の公開の 9 字句は変えない — 誤りなら 4 つの固定テンプレートとキーの規則を足す
- R7: グリフの部分ごとに `fetchedAt` を持ち、`EntryMeta.fetchedAt` は最も新しい部分の値にする — m4 の削除期限の掃除はレコードごとに消すので、新しい部分を巻き添えにしない。古い部分は配信の時点で無いもの — 誤りなら古い部分がレコードの中に残る（大きさは m4 の掃除で部分ごとに落とす形を足す）
- R8: `asset` の URL 配列はミラー — §5.1 の「URL 配列（ミラー）は 1 つの Resource」と揃える — 誤りなら別々の資源を 1 回で登録したい利用者は `register` を複数回呼ぶ
- R9（P1）: 範囲を持つのは tile の Resource と `raster`・`vector` の Source だけで、範囲だけの合流は tile どうしの衝突に限る — 今は tile でない Source が「範囲の指定なし＝全域」として tile の Resource の範囲を広げる — 誤りなら型の違う衝突でも範囲を足す規則を書き直す
- R10（P2）: スタイルの `update()` で新しく現れた子の衝突は新しい登録として扱い（範囲だけ＋`warnings`）、前からある子の衝突は keep — §5.6 の「スタイルの下位資源のときは…スタイルの残りは更新する」を新しい子にも当てる。例外にするとスタイル全体が更新できなくなる — 誤りなら update() が新しい子の衝突で失敗する
- R11（人間の判断 1・推奨案を採った）: `mapbox://` を標準で載せる（`providers/mapbox.ts` を配布物に含め、配線が既定で渡す）。範囲取得も止めず、README に「提供元の利用規約の確認は利用者の責任」と書く — #40 の完了条件どおり — 誤りなら標準の提供元の一覧から外し、`addProvider` の例として文書にだけ残す（1 行の変更）
- R12（人間の判断 2・推奨案を採った）: 旧 API は本サイクルでは非推奨にしない。Maplat#254 の完了後のトレインでリリースポリシー §9.1 の手順に入り、2.0 で消す。JSDoc の `@deprecated` も付けない — 利用側 3 製品がまだ `registerMap` を呼んでいる（仕様 §13）— 誤りなら後のトレインで非推奨の 3 点を入れるだけ
- R13: 提供元の登録表は `plugins.ts`（モジュール変数の唯一の置き場）、標準の `mapbox` は配線が context に渡し、利用者の提供元を先に評価する — §3 で `plugins.ts` は `providers/` を import できない（m2-t1 の Ruling）。先に評価すれば標準を差し替えられる — 誤りなら標準を先にし、差し替えは同じ id の登録で行う
- R14'（m2 R14 を置き換える）: WebKit は CI（GitHub の ubuntu。毎回 install するので共有キャッシュに触らない）で測る。手元は Chromium だけのまま。Firefox は CI で 1 回試し、SW が準備できなければ未確認のまま理由を書く — 手元の `playwright install` は共有キャッシュの他の版を消す（実績あり）。iOS の利用者がいるので WebKit は測る価値が高い — 誤りなら Linux の WebKit と iOS Safari の差が残る（README に書く）
- R15: 依存（npm パッケージ）を足さない。`maplibre-gl` は e2e でも使わず、blob Worker から同じ形の要求を出す。`@c4h/beatbox` は変換表を写して突き合わせの試験に表で持つ — 実行時依存 0 件を保つ（仕様 §10・§14.1）。e2e の確かめたいのは SW の捕捉で、MapLibre の描画ではない — 誤りなら MapLibre の要求の形の変化に気づくのが利用側の試験になる
- R16: §5.2 の `httpUrl`（#14）は要らない — 提供元の URL は登録の時点で https に解決し、`templates` が資格情報なしの URL を持つ。親の `spec.url` が地図ライブラリへ渡す https の URL — 誤りなら元の `mapbox://` を記録する項目を足す
- R17: MLT 1.3.0 の空本体は F1 で確認済みとし、m3 では試験を足さない — 実体のコードを読んだ — 誤りなら MLT の利用者でベクタの範囲外が描画で落ちる
- R18: `removeResource(resourceId)` はその Resource の Entry を消し、Resource の記録と捕捉は残す。他の Source と共有していても、範囲だけ（`rangeOnlySourceIds`）で参照している Resource でも消す（第 1 回 C-O13）。直列の待ち行列に通す。見つからなければ新しい code `resource-not-found` — Resource は Source の指定から作られるので記録を消しても update で戻る。名指しの削除は利用者の意図で、`clean()`（共有を残す）と役を分ける — 誤りなら共有のときは拒否する形へ直す
- R19: `usage()` は `{ count, bytes, byProvider }`。全 Resource（旧 API を含む）を数え、鍵は `provider` か origin — 保存の量を見るための API なので旧 API の地図も入れる — 誤りなら旧 API を外すか `legacy` の鍵にまとめる
- R20: `warnings` の code に `fetch-failed`・`same-origin-skipped`・`unsupported-source` を足す（subject は Resource.id か、無ければ正規化したテンプレートか `sources.<名前>`）— §12 は「利用者は知らない code を無視する」としているので足せる。資格情報は正規化で落ちる — 誤りなら公開の前の水準 2 で直す
- R21（I1）: 登録の資格情報は差し込み口の後の要求のオリジンが元と同じときだけ足し、ヘッダの資格情報を足した要求は `redirect: 'error'` で出す — SW は `redirect: 'manual'` の行き先を読めないので、別オリジンへのリダイレクトでヘッダが付いて行くのを止める手段がこれだけ。クエリの資格情報は最初の相手が既に受け取っている — 誤りならヘッダ認証で別オリジンへリダイレクトする上流が使えない（README に書く）
- R22（I2）: ミラーの間で同じ資格情報の名前に違う値があれば `attribute-invalid` — 1 つにまとめると別のホストへ別のホストの鍵が送られる。ミラーごとの Source なら m2 の I2 の規則（オリジンで選ぶ）で正しく送れる — 誤りなら利用者が Source を分ける手間が増えるだけ
- R23（I9。第 1 回 X4 で decode を足した）: パスの区画の `sk.` の検査は `sk.eyJ` に絞り、クエリと資格情報の値は `sk.` のまま。キーの残りのクエリから、decode した後の名前か値が `sk.` で始まる項目を除く — パスには `sk.osm` のような正当な名前があり、Mapbox の秘密トークンは `sk.eyJ` で始まる。キーに秘密を残さない — 誤りなら `sk.eyJ` で始まらない秘密のパスが通る（Mapbox 以外の例は知られていない）
- R24（I4）: `WeiwudiError.from` は印のある WeiwudiError の未知の code を保ち、`WeiwudiErrorCode` と `ResourceType` は閉じた union のまま文書で「増える」と書く — 開いた union（`string & {}`）は補完と網羅性の検査を失う。印のある値は別のコピーの Weiwudi が作ったもの — 誤りなら union を開く（公開前なら破壊にならない）
- R25（I6）: 制御の POST は要求元の client の URL のオリジンが SW と同じときだけ受ける — SW の `fetch` は制御下の client からしか来ないので多重の守り。値は安い — 誤りなら blob 以外の特殊な client（`about:srcdoc` など）からの制御が通らない（t10 で srcdoc を測る）
- R26（I10）: 同じ要求に当たる別の照合の形は `template-shadowed` の警告のまま — 自動で合流させるとキーの形が違う Resource の統合になり、§5.6 の「統合はしない」に反する — 誤りなら後の登録が黙って捕捉されない（警告と文書で知らせる）
- R27（I5）: 定数は依存の無い `constants.ts`、SourceRecord を読む小さな補助は `store.ts` に置く — §3 で `control.ts` は `url_pattern` を、`spec.ts` は `store` の値を import できず、全ファイルが読める置き場が要る — 誤りならファイルが 1 つ余るだけ
- R28（第 1 回 C-S4・C-S1 で失敗の扱いを置き換えた）: スタイル・TileJSON の本体の書き換え（提供元の `rewriteStyle` と資格情報の除去）は `ServeInput.transform` 1 つで行い、保存と配信に同じ本体を使う。**`transform` が投げたら（JSON でない・除去の失敗）上流の失敗（HTTP）として §6 の 4・5 にし、保存しない** — 地図ライブラリは `mapbox://` を解釈しない（§2）ので配信にも要る。HTML のログイン画面や除去しそこねた本体をスタイルとして固定しない — 誤りなら読めないスタイルを上流のまま配信だけする形へ分ける
- R29: スタイルの子の範囲外の応答は型の既定（ラスタは透明 PNG、ベクタは空本体）— `kind: 'style'` の `SourceSpec` に `outOfRange` は無い。地図ライブラリは TileJSON の範囲の外を要求しない — 誤りなら `style` に `outOfRange` を足す（minor で足せる）
- R30（第 1 回 C-S3・X6・X7 で置き換えた）: 新しい登録で `invalid-style` か途中の失敗が起きたら、子を外してから親を外す順で巻き戻す。既存の登録の `update()`・再登録は、段 A（前の style 子の方針でのスタイルの取得と解析）が成功するまで親・子・資格情報・CORS の印のどれも書き換えない — §5.5 の「スタイル自体が読めなければ invalid-style」と、読めないときに何も変えないことを保つ。前の版の「段 A は前の子を外さないので巻き戻しが要らない」は、段 A で親・資格情報を先に書き、`resetCors` で CORS の印を消すので誤りだった — 誤りなら新しい登録で Source だけ残る形へ（利用者が `remove()` で外す）
- R31: `raster-dem` は `encoding: 'raster'` の tile、`video` は `unsupported-source` で登録しない — `video` は Range 要求で取られ、§11 で素通しになるので保存できない — 誤りなら video の URL を `data` として登録する（Range で素通しのまま）

- R32（第 1 回 C-S1・X5・新規）: スタイル・TileJSON の本体から資格情報の項目を除くのは、子として捕捉され、かつ R5 で親の資格情報を受け取る URL だけ。相対 URL は base で絶対化してから判定する — 別ホストの子や子にならない URL のトークンを消すと、SW が足す相手でないので上流が 401 を返す。逆に R5 で SW が足す URL は、本体から除いても SW が足すので失うものが無い（仕様 §10 の理由と同じ） — 誤りなら本体にトークンが残る範囲が広がる（そのトークンはもともとページの JS から見える）
- R33（第 1 回 C-S3・X7・新規。進行役の Ruling）: 段 A より後の IndexedDB の失敗は巻き戻さず、部分的な状態を受け入れる（次の `register`・`update` で直る）。直列の外の読み取り（`source()`・`sources()`・`stats()`）で段の途中の状態が見えることも受け入れ、文書に書く — IndexedDB の失敗はまれで、動くもの最優先。読み取りまで直列にすると上流の取得の間ずっと読めなくなる — 誤りなら壊れた登録を利用者が `remove()` してから登録し直す
- R34（第 1 回 C-O14・新規）: スタイルの登録は直列の待ち行列の中で上流の取得を待ち、その間の他の書き換えの操作は待たされる。m3 では上限を置かず文書に書く — 待ち行列の外で取得すると、段の途中で同じ Source の別の操作が割り込む — 誤りなら遅い上流で他の操作が長く待つ（m4 で上限を検討する。state の m4 の「変更の op も待ち続ける」と同じ所）
- R35（第 1 回 C-S2・新規）: 同じオリジンの検査（§5.5-5）は、スタイルの参照だけでなく TileJSON の `tiles` にも当てる。スタイルか TileJSON のどちらかが SW と別オリジンなら、SW と同じオリジンの URL を子にしない — 第三者の TileJSON 経由でも同じオリジンの API を捕捉させない — 誤りなら同じオリジンのスタイルが別オリジンの TileJSON 経由で同じオリジンを指す正当な構成が捕捉されない（`raster`・`vector` で直接登録すれば足りる）
- R36（第 1 回 C-S6・X3・新規）: `same-origin-skipped` の subject はクエリを落とした URL（オリジン＋パス）で、パスに秘密を見つけたら `sources.<名前>` にする — 子にならない URL は正規化（資格情報の除去）を通らないので、クエリをそのまま書くと `?foo=sk.…` が公開の値に出る — 誤りなら subject が少し分かりにくくなるだけ
- R37（第 1 回 C-O5・新規）: 同じ id で `kind` を替えた登録は `attribute-invalid` — 子の構成が丸ごと変わり、keep（S-I）の規則が当たらない — 誤りなら利用者が `remove()` してから登録し直す手間が増えるだけ

## 未決の点（事前点検と実装で決める）

- U1: TileJSON の `bounds` があって `maxzoom` が無いときの既定を 30 にした（R29 の近く。TileJSON 3.0 の既定は 30）。Mapbox の TileJSON は `maxzoom` を持つので実害は無い見込み。t7 の実装で他の配信元の例を見て変えてよい
- U2: Firefox が CI の Playwright で SW を準備できるか（t10 で測る。m1 では手元で返らなかった）
- U3: WebKit だけで落ちる不具合が出たときの量（t10。直せる範囲は t10 で直す決まりにしたが、多ければタスクを分ける）
- U4: `usage()` に `navigator.storage.estimate()` の値を足すか（今回は足さない。要望が出たら minor で足す）
