```ts
export function openStore(): Promise<Store>;   // 接続を使い回す。onversionchange で閉じる
export interface Store {
  getSource(id: string): Promise<SourceRecord | undefined>;
  putSource(rec: SourceRecord): Promise<void>;
  listSources(): Promise<SourceRecord[]>;
  deleteSource(id: string): Promise<void>;           // sources と credentials と regions（sourceId）を消す
  getResource(id: string): Promise<ResourceMeta | undefined>;
  putResource(meta: ResourceMeta): Promise<void>;
  resourcesBySource(sourceId: string): Promise<ResourceMeta[]>;          // sourceIds 索引
  resourcesByRangeOnlySource(sourceId: string): Promise<ResourceMeta[]>; // rangeOnlySourceIds 索引
  listResources(): Promise<ResourceMeta[]>;
  deleteResource(id: string): Promise<void>;         // 同じ tx で entries と bodies をキーの範囲で消す
  clearEntries(resourceId: string): Promise<void>;   // Resource は残し、count・bytes・pinnedBytes を 0 に
  getEntry(key: string): Promise<{ meta: EntryMeta; body: EntryBody } | undefined>;
  hasEntries(keys: string[]): Promise<boolean[]>;    // getKey だけ。本体を読まない
  touch(key: string, accessedAt: number): Promise<void>;  // entries だけを書く
  putEntry(meta: EntryMeta, body: EntryBody, evict?: { resourceIds: string[]; maxBytes: number }): Promise<{ saved: boolean }>;
  getCredentials(sourceId: string): Promise<Credentials | undefined>;
  putCredentials(sourceId: string, c: Credentials): Promise<void>;
  kvGet<T>(key: string): Promise<T | undefined>;
  kvPut(key: string, value: unknown): Promise<void>;
}
```

- `putEntry` は 1 つの `readwrite` トランザクション（`entries`・`bodies`・`resources`）で、退避・保存・`count`／`bytes` の更新を行う。**退避の規則は現行の `putItemWithEviction` と同じ**: 退避の候補は `evict.resourceIds` の Entry のうち `pinned = 0` のもの（`[resourceId, pinned, accessedAt]` を `resourceId` ごとに引いて併合）を `accessedAt` 昇順・同値はキー昇順。保存する場合は同じキーを候補から外し、`budget = maxBytes - 新しい大きさ`。単体で `maxBytes` を超える応答は保存しないが、候補の合計を `maxBytes` まで減らす退避は行う（現行と同じ）。`maxBytes` が 0 なら保存しない
- **reject する値は必ず `DOMException` か `Error`**（`tx.error`・`req.error`）。`Event` を reject しない（仕様 §9 の既知の変化「`[object Event]`」をここで終わらせる）
- `onblocked` と `onversionchange` の扱いは現行の `openDatabase`（#59）をそのまま移す。文面の DB 名は `WeiwudiStore`
- 旧 DB（`Weiwudi`・`Weiwudi_<id>`）には触らない（移行は m4）

### 試験

`tests/unit/store.test.ts`:

- 各操作の往復。`deleteResource` が他の Resource の Entry を残すこと
- **数の一致**: 乱数の種を固定した 300 回の `putEntry`（退避あり・なし・同じキーの上書き・大きすぎる応答を混ぜる）と `deleteResource`・`clearEntries` の後で、全 Resource の `count`・`bytes` が `entries` を全件数えた値と一致する
- 退避の順: `accessedAt` が同じときキー昇順（例 `map:m\x002_10_0` が `map:m\x002_1_0` より先）。旧 API の `putItemWithEviction` の試験と同じ入力で同じキーが残る
- `touch` は `bodies` へ書かない（`IDBObjectStore.prototype.put` の spy で `bodies` への呼び出しが 0）
- 保存の abort（m1 の `abortPutAfterSuccess` と同じ形）で、reject の値が `name === 'QuotaExceededError'` の `DOMException`
- 仕様 §13 の「書き換える」の :553・:563 に当たる 2 件: 閉じない別の接続が残っても止まらず `BlockedError` を返し、閉じた後は開ける／別の SW が開いたままでも `onversionchange` で譲る

## Ruling

- R1: t5（載せ替え）を t7（捕捉）より前に置く — 旧 API の試験と golden が新コアの誤りを先に出す — 誤りなら捕捉の不具合がコアの不具合と混ざって出る（並べ替えるだけで済む）
- R2: タイルのキーの suffix を全資源で `z_x_y` にする（仕様 §5.3 を変更）— 旧キーと同じ形なので、`accessedAt` が同じときの退避の順（キー昇順）が旧 API と一致し、m4 の移行もキーを作り直さずに済む。`z/x/y` だと `2/1/0` と `2/10/0` の順が `_` のときと逆になる — 誤りなら退避の順が旧実装とずれ、golden の突き合わせで落ちる
- R3: 合流と実効方針（§5.6）を m3 から m2 へ前倒しする — `raster` どうしでも同じ URL の登録は起き、m2 で仮の動き（拒否や上書き）を作ると m3 で作り直しになる — 誤りなら m2 が大きくなるだけ（t6 は独立していて並行できる）
- R4: m2 の `register` は `raster` と `vector` を受け、他は `unknown-type` で拒否する — `vector` は範囲外の `empty` が `serve()` に入れば足りる。スタイル・`asset` は芋づる登録（m3）が要る — 誤りなら m3 で `kind` の分岐を足すだけ
- R5: 汎用の資格情報（`credentials` ストア・`credentialParams` によるキーからの除去・要求に無いときだけ足す）を m2 に入れ、提供元（`mapbox`・`sk.` の検査）は m3 に残す — キーの形（§5.3）と保存の可否（§4.6）に資格情報が要り、後から入れるとキーが変わる — 誤りなら m3 の提供元の作業が減るだけ
- R6: テンプレートの展開は `tile_math.expandTileTemplate` 1 つにし、旧 API は引数なし（最初の出現だけ・4 字句）、新 API は `{ all: true }` で呼ぶ — 旧の癖は公開の挙動で変えられず、別の関数にすると二重実装になる — 誤りなら引数の分岐が 1 つ増えるだけ
- R7: `serve()` は上流の取り方を引数で受ける — 旧 API は `fetch(url 文字列)` の 1 引数でなければ試験 :228・:239 が落ち（m1 第 3 回で実測）、実 URL は §4.5 の組み替えが要る。取り方以外の決定（§6 の表）は 1 つ — 誤りなら引数が 1 つ減るだけ
- R8: hit の `touch` を待つかは t5 の golden で決める（待たなくても `stats` が合えば待たない）— 配信を IndexedDB の書き込みで遅らせたくない。旧 API の試験の順序に効くかは実測でしか分からない — 誤りなら golden が落ちるので待つ形に戻す
- R9: 合成した応答すべてに `access-control-expose-headers: x-weiwudi-status, x-weiwudi-error` を付ける（申し送り 2）— Chromium では無くても読めたが、ブラウザによって CORS のフィルタが掛かるおそれがあり、付けても害が無い — 誤りならヘッダが 1 つ余るだけ
- R10: opaque の判定は `response.type === 'opaque'` だけで行う — Node では opaque を作れず、試験はハーネスの偽物を使う。`status === 0` などを併用すると偽物と実物で判定がずれる — 誤りなら実ブラウザの e2e（t9）で落ちる
- R11: 旧 API の `fetchAll` を開始の `FetchEvent` の `waitUntil` に結ぶ — 応答の形は変えず、SW が途中で止まる確率だけが下がる（仕様 §7.2）。再開（`resume`）は m4 — 誤りならブラウザの上限（数分）で止まるのは今と同じ
- R12: `warnings` は `"<code>: <subject>"` の文字列（`subject` は `Resource.id` かクエリを除いた URL）とする — 仕様 §12 の `string[]` を保ち、機械でも `code` を取り出せる。クエリを除くのは資格情報を出さないため（§10）— 誤りなら公開前（水準 2 のレビュー）に形を直す
- R13: 範囲取得側の CORS・認証の規則（`jobOpaqueStreak`・5 枚の確かめ・401・403 で止める）は m4 の `fetchRange` と一緒に入れる — m2 のジョブは旧 API の `fetchAll` だけで、旧 API は `fetch(url 文字列)` の取得なのでこの規則を使わない — 誤りなら m4 で `upstream.ts` に関数が 1 つ増える
- R14: Firefox は m2 でも試さない — Playwright 組み込みの Firefox で SW の準備が返らないことを m1 で確かめた。WebKit だけ任意の project で測る — 誤りなら Firefox 固有の不具合が公開後に見つかる（README に未確認と書いて利用者に知らせる）
- R15: `QuotaExceededError` のときの全体 LRU の退避と再試行（仕様 §7.1）は m4 にする — 入れると旧 API の試験「保存の abort（QuotaExceededError）→ 保存されない」の結果が変わり、旧 API の挙動の変化になる。m4 の全体上限と一緒に、旧 API の扱いを決めて入れる — 誤りなら m2〜m4 の間はブラウザの上限に当たった後の自力の回復が無い（現行と同じ）
