## m2-t2: `store.ts`（#37）

コミット種別: `refactor:`（内部。t5 まで使われない）

### 対象ファイル

### 作るもの

仕様 §5.2 の型（`ResourceMeta`・`TileExtent`・`ResourcePolicy`・`EntryMeta`・`EntryBody`・`ResourceType`・`OutOfRange`・`ResourceInfo` と射影 `toResourceInfo(meta, now, sourceId?)`。`rangeOnly` は `sourceId` が `rangeOnlySourceIds` にあるときだけ出す。`sourceId` を渡さない呼び出し（差し込み口）では出さない。第 2 回 O6）と `SourceRecord`（`id`・`kind`・`spec`（資格情報を除く）・`order`（登録順の連番）・`warnings: string[]`（第 1 回 S13）・`createdAt`・`legacy?: MapSetting`）。

単一 DB `WeiwudiStore`・`version: 1`・仕様 §5.4 の 7 ストアと索引。

```ts
export function openStore(): Promise<Store>;     // context が 1 つ持つ。onversionchange で閉じる
export interface Store {
  getSource / putSource / listSources / deleteSource(id)   // deleteSource は credentials と regions（sourceId）も消す
  getResource(id) / listResources() / resourcesBySource(sourceId) / resourcesByRangeOnlySource(sourceId)
  createResource(meta): Promise<void>;                     // 無いときだけ。あれば reject
  replaceResource(meta): Promise<void>;                    // registry 用。同じ tx で count・bytes・pinnedBytes は保存済みの値を引き継ぐ
  patchResource(id, fn: (m: ResourceMeta) => ResourceMeta | undefined): Promise<ResourceMeta | undefined>; // 1 tx で読み・直し・書き（第 1 回 S2）
  deleteResource(id): Promise<void>;                       // 同じ tx で entries と bodies をキーの範囲で消す
  clearEntries(resourceId): Promise<void>;                 // 同じ tx で count・bytes・pinnedBytes を 0 に
  getEntry(key): Promise<{ meta: EntryMeta; body: EntryBody } | undefined>;
  hasEntries(keys: string[]): Promise<boolean[]>;          // getKey だけ
  touch(key, accessedAt): Promise<void>;                   // entries だけ。**tx は呼び出しの中で同期に作る**（第 1 回 O-6）
  putEntry(meta, body, evict: { resourceIds: string[]; maxBytes: number }[]): Promise<{ saved: boolean }>;
  getCredentials / putCredentials(sourceId, c)
  kvGet / kvPut
}
```

- `putEntry`（1 つの `readwrite` tx・`entries`・`bodies`・`resources`）:
  - **同じ tx で Resource の有無を見て、無ければ保存しない**（`saved: false`。消された Resource へ書き込みを残さない。第 1 回 O-7）
  - 退避は `evict` の**要素ごとに**行う（第 1 回 S4）。各要素について、`resourceIds` の Entry のうち `pinned = 0` のものを `[resourceId, pinned, accessedAt]` で引いて併合し、`accessedAt` 昇順・同値はキー昇順で消す。規則は現行の `putItemWithEviction` と同じ: 同じキーは候補から外し、`budget = maxBytes − 新しい大きさ`。単体で `maxBytes` を超える応答は保存しないが、その要素の退避は行う。どれか 1 要素でも「保存しない」なら保存しない。`maxBytes` が 0 なら保存しない（旧実装と同じ。第 2 回 O16）
  - Entry の増減と同じ tx で各 Resource の `count`・`bytes` を直す
- reject する値は必ず `tx.error`・`req.error`（`DOMException`・`Error`）。`Event` を reject しない（仕様 §9）
- `onblocked`・`onversionchange` は現行の `openDatabase`（#59）を移す。文面の DB 名は `WeiwudiStore`
- 旧 DB（`Weiwudi`・`Weiwudi_<id>`）には触らない

### 試験

`store.test.ts`:

- 往復。`deleteResource` が他の Resource の Entry を残す。`createResource` の重複は reject
- **数の一致**: 種を固定した 300 回の `putEntry`（退避あり・なし・上書き・大きすぎる応答・上限 2 つ）と `deleteResource`・`clearEntries` の後で、各 Resource の `count`・`bytes` が `entries` の全件の集計と一致する
- **交互の更新**（第 1 回 S2）: 2 つの `patchResource` を同時に出しても両方の変更が残る。`replaceResource` が同じ tx で `count`・`bytes` を引き継ぐ（保存と並べても消えない）
- 退避の順: `accessedAt` が同じときキー昇順（`map:m\x002_10_0` が `map:m\x002_1_0` より先）。旧 API の `putItemWithEviction` の試験と同じ入力で同じキーが残る
- **上限 2 つ**（第 1 回 S4）: 1 つの Resource を 2 つの Source が上限つきで参照するとき、両方の上限を満たすまで消える
- `putEntry` が、同じ tx の前に消された Resource には書かない（`saved: false`・`entries` が増えない）
- `touch` は `bodies` へ書かない（`IDBObjectStore.prototype.put` の spy）。`touch` の呼び出しが戻った時点で tx が作られている（`IDBDatabase.prototype.transaction` の spy が同期で呼ばれている）
- 保存の abort で、reject の値が `name === 'QuotaExceededError'` の `DOMException`
- `maxBytes` が 0 の上限では保存しない（第 2 回 O16）
- `toResourceInfo`: 範囲だけの Resource で `sourceId` を渡すと `rangeOnly: true`、渡さないと出ない。`corsless` は `corslessUntil` が今より先のときだけ。保存の項目（`corsOk`・`policy` など）が出ない（第 2 回 O6）
- 仕様 §13 の :553・:563 に当たる 2 件（`blocked` で止まらない・`onversionchange` で譲る）

## Ruling

- R1: t5（載せ替え）を t7（捕捉）より前に置く — 旧 API の試験と golden で新コアの誤りを先に出す — 誤りなら並べ替えるだけ
- R2: タイルのキーの suffix を全資源で `z_x_y` にする（仕様 §5.3）— m4 の移行で旧キーの suffix を解析し直さずに使える。あわせて `accessedAt` が同じときの退避の順も旧 API と揃う — 誤りなら移行でキーの組み直しが要る
- R3: 合流と実効方針（§5.6）を m2 へ前倒しする — `raster` どうしでも同じ URL の登録は起き、仮の動きを作ると m3 で作り直しになる — 誤りなら m2 が大きくなるだけ
- R4: m2 の `register` は `raster` と `vector` を受ける — `vector` は範囲外の `empty` だけで足りる — 誤りなら m3 で分岐を足すだけ
- R5: 汎用の資格情報を m2 に入れ、提供元（`mapbox`）は m3 に残す — キーの形と保存の可否に要り、後から入れるとキーが変わる — 誤りなら m3 の作業が減るだけ
- R6: テンプレートの展開は `tile_math.expandTileTemplate` 1 つにし、旧 API は引数なし、新 API は `{ all: true }` で呼ぶ — 旧の癖を残しつつ二重実装を避ける — 誤りなら引数の分岐が 1 つ増えるだけ
- R7: `serve()` は上流の取り方を引数で受ける — 旧 API は `fetch(url 文字列)` の 1 引数でないと :228・:239 が落ちる。取り方以外の決定は 1 つ — 誤りなら引数が 1 つ減るだけ
- R8（第 1 回 O-6 で置き換え）: hit の `touch` は応答の前に呼んで tx を同期に作り、完了は待たない — 配信を書き込みで遅らせず、hit の直後の退避で hit したキーが消えない — 誤りなら t4 の「hit の直後に退避」の試験で落ちる
- R9（第 1 回 O-16 で理由を直した）: 合成した応答すべてに `access-control-expose-headers: x-weiwudi-status, x-weiwudi-error` を付ける — SW が合成した応答は Fetch の仕様では `basic` 扱いでフィルタが掛からないはずだが、WebKit・Firefox を測っていないので、付けて害の無い保険とする。公開の契約（仕様 §6）にも含める — 誤りならヘッダが 1 つ余るだけ
- R10: opaque の判定は `response.type === 'opaque'` だけで行う — 試験の偽物と実物で判定がずれない — 誤りなら t9 の実ブラウザで落ちる
- R11: 旧 `fetchAll` を開始の `FetchEvent` の `waitUntil` に結ぶ（再開は m4）— 応答の形を変えずに途中停止を減らす — 誤りでも止まり方は今と同じ
- R12: `warnings` は `"<code>: <subject>"` の文字列で、登録・`update` の時点の写し — 仕様 §12 の `string[]` を保ち、資格情報を出さない — 誤りなら公開前の水準 2 で直す
- R13: 範囲取得側の CORS・認証の規則は m4 の `fetchRange` と一緒に入れる — m2 のジョブは旧 API の `fetchAll` だけで、この規則を使わない — 誤りなら m4 で関数が 1 つ増える
- R14（第 1 回 O-13 で改めた）: m2 では WebKit も Firefox も測らず、`playwright install` もしない — 1.64 の要求する版が手元に無く、入れると共有キャッシュに触る — 誤りなら他のエンジン固有の不具合が公開後に見つかる（README に未確認と書く）
- R15: `QuotaExceededError` のときの全体 LRU の退避と再試行は m4 — 入れると旧 API の試験「保存の abort → 保存されない」の結果が変わる — 誤りなら m4 まで、上限に当たった後の自力の回復が無い（現行と同じ）
- R16（台帳の進行役の Ruling と同じ）: 制御の POST は preflight の要らない単純要求（`text/plain;charset=UTF-8` の JSON）にする — preflight が SW に届くかに依存しない — 誤りなら t9 の測定で落ちるので `OPTIONS` の扱いへ切り替える
- R17: 実行中の状態は `Weiwudi_Internal` の呼び出しごとの `context` に置き、モジュール変数は `plugins.ts` の登録表だけにする（第 1 回 S1）— 試験の 1 ハーネスが 1 SW になり、2 SW の試験が本物になる。`addPlugin` は SW スクリプトの先頭で呼ぶので大域で足りる — 誤りなら 2 SW の試験が偽の緑になる（t7 の対照で分かる）
- R18: その版が扱わない `kind` は新しい code `unsupported-kind` で拒否する（推奨）— `unknown-type` は旧 API の文面つきの code で、意味も「知らない値」と違う。公開の前に union へ入れておけば、m3 で `style`・`asset` を受けるときに利用者の分岐を壊さない — 誤りなら code が 1 つ余る
- R19: 候補の条件（`navigate`・script を除く）を照合ルートにも当てる（第 1 回 O-8）— 登録したテンプレートがページや script の URL に重なっても捕捉しない。門番と同じ関数 1 つで済む — 誤りなら CSS 経由などの珍しい destination の要求が捕捉されない
- R20: `opaque` イベントは m4 に回す（第 1 回 O-10）— 新 API のページ側イベントの通り道は m4 の範囲取得のイベントと一緒に作る。m2 では `ResourceInfo.corsless` で見える — 誤りなら m2〜m4 の間は CORS 非対応への切り替えに気づくのが `resources` を読んだときになる
- R21: 配信の時点で削除期限を過ぎた Entry を「無いもの」として扱うのは m2 から（第 1 回 O-12）— `serve()` の条件 1 つで、m4 の掃除と独立している。m2 で方針を受け付けるのに効かないのを避ける — 誤りなら m4 で入れるのと同じ
- R22: `NormalizedSpec`（`spec.ts`）は t3 に置く（第 1 回 O-18）— t6 の前に要り、`url_pattern` と同じく純粋な検査の層である — 誤りならタスクを 1 つに分けるだけ
- R23: 依存の決まりは仕様 §3 の表 1 つにし、`tests/unit/deps.test.ts` で機械に確かめる（第 1 回 O-2）— 表を計画に写すと 2 か所が食い違う。grep では複数行の import と `export … from` を取りこぼす — 誤りなら試験の表を直すだけ
- R24: `sk.` の拒否は提供元に依らない文字列の検査として m2 に入れる（第 1 回 C6）— m2 で通った登録が m3 で失敗し、その間に秘密トークンが保存されるのを防ぐ — 誤りなら `sk.` で始まる正当な値が拒否される（Mapbox 以外でそういう形の公開トークンは知られていない）
- R25: t3 を t2 の後に置き、並行の組を「t3 と t4」「t6 と t5」にする（第 2 回 O14）— `NormalizedSpec` が `store.ts` の型（`ResourcePolicy` など）を `import type` で使うので、t2 と並べると型の置き場が 2 つになる。`deps.test.ts` は t1 で全行を持たせ、並行の PR が同じファイルを触らないようにする — 誤りなら並行の機会が 1 つ減るだけ
- R26: タイルのキーの suffix は `tile_math.tileKeySuffix` 1 つで作り、`url_pattern` と `legacy` の両方が使う（第 2 回 O12）— `legacy.ts` は §3 の表で `url_pattern` を import できず、別々に書くと二重実装になる — 誤りなら関数の置き場を変えるだけ
- R27: `/v2/ping` の GET の振り分けは `weiwudi_gw_logic.ts`（配線）で行う（第 2 回 O12）— `legacy.ts` から `control.ts` を呼ぶと依存が逆になる。配線は全部を import してよい層である — 誤りなら振り分けの 1 行を移すだけ
- R28: m2 では `url_pattern` に展開の関数を置かない（第 2 回 O13）— m2 で新 API が展開を使うのは試験だけで、薄い委譲の関数は使い道のない公開面になる。m4 の範囲取得は `tile_math.expandTileTemplate` を直接呼ぶ — 誤りなら m4 で 1 行の関数を足す
- R29: `ensureV2()` の成功は controller の実体ごとに記憶し、`controllerchange` で捨て、200 で正しい JSON 以外はすべて失敗にする（第 2 回 D2。fail-closed）— 資格情報の入った POST を古い SW や別の SW へ出さない。失敗を記憶しないので、更新の後は次の呼び出しで通る — 誤りなら ping が 1 回余るだけ
- R30: `sk.` の検査は、`credentials` の各値とテンプレートの全クエリ値について、`Bearer `・`Token `・`Basic ` の前置きを剥がしてから先頭を見る（第 2 回 D5）— 値の先頭だけでは `Authorization: Bearer sk.…` と、`credentialParams` に無いクエリ項目のトークンを見逃す — 誤りなら `sk.` で始まる正当な値が拒否される（第 1 回 R24 と同じ）
- R31: userinfo（`user:pass@`）を含むテンプレートは登録で拒否する（第 2 回 D1）— 取り除くと地図ライブラリの要求と照合が合わなくなり、残すと id・テンプレート・`warnings` に出る。タイル配信で userinfo を使う例は知られていない — 誤りなら userinfo つきの URL の利用者は `credentials.headers` に移す必要がある
- R32: `addPlugin` は同じオブジェクトの 2 回目を無視し、以後に始まる要求にだけ効き、`state` はプラグインごと・要求ごとに作る（第 2 回 D4・推奨）— Workbox のプラグインと同じ扱いで、SW スクリプトの再評価や二重の import で同じプラグインが 2 回走らない — 誤りなら同じプラグインを 2 回走らせたい利用者は別のオブジェクトを渡す
